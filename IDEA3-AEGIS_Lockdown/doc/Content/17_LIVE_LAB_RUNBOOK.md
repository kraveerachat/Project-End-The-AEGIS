# 17 — IDEA3 Live Lab Runbook (Core-local AP, TLS MQTT, ESP32, relay)

Status: lab procedure proven once on 2026-10-23 against `main` `cc096de` plus the graduated-response and Telegram-delivery
patches (see `18_LIVE_LAB_ACCEPTANCE_SUMMARY.md`). Not deployed to production. Scripts: `deploy/live-lab/`.

## Topology

```
 Internet (USB tether / any uplink)  <- only the host's default route; the lab never touches it
        |
   [ Core host ]-- Wi-Fi interface = lab AP (SSID AEGIS-IDEA3-LAB, WPA2, 10.77.30.1/28, never-default)
        |  dnsmasq (DHCP + Core-local DNS, no router option)   chrony (NTP for the ESP32, kernel-synced)
        |  mosquitto (TLS 1.2, 8883, password + ACL, no plaintext)   Core (transient unit, protocol v1)
        |
   ESP32 (Wi-Fi client, GPIO27) -> ULN2003 -> relay module -> cable under protection (tester pin 2)
```

- The AP interface is dedicated to the lab. Never join it to another Wi-Fi network; the bring-up script turns off
  autoconnect on every other Wi-Fi profile and records them for the rollback.
- The broker certificate has a DNS SAN only (`mqtt.aegis.home.arpa`). The Core connects to the AP address and verifies the
  name through `AEGIS_MQTT_TLS_SERVER_NAME`; dnsmasq answers that name with the AP address.
- The host firewall table (`inet aegis_live`, derived from main's AP isolation template) lets the AP clients reach only
  DHCP, DNS, NTP and 8883. The ESP32 therefore does not answer ping; that is by design, not a fault.
- Everything runs as transient systemd units (`aegis-live-*`). Nothing is installed or enabled.

Work directory `~/aegis-live-lab` (override with `AEGIS_LIVE_DIR`), containing:

Create them with the tooling already in the repository (`deploy/pr11-phase4/`, `aegis_soc.cli restore-credential`,

Host tools: NetworkManager (`nmcli`), nftables, dnsmasq, chrony, mosquitto, openssl, systemd, python3.

## Start / stop

```bash
cp deploy/live-lab/live-lab.env.example ~/aegis-live-lab/live-lab.env   # edit AP_IFACE, INTERNET_IFACE, STOP_UNITS
deploy/live-lab/aegis-live-up.sh --render-only    # optional: render configs into etc/ and stop (changes nothing else)
deploy/live-lab/aegis-live-up.sh                  # AP, dnsmasq, chrony, mosquitto, Core, then a health summary
deploy/live-lab/aegis-live-down.sh                # stop units, delete firewall table, drop AP profile, restore Wi-Fi autoconnect
```

`aegis-live-up.sh` refuses to continue unless the default route is on `INTERNET_IFACE` and a DNS name resolves, and it
checks both again after the AP is up; if the route changed it stops and tells you to run the down script. Colliding
units listed in `STOP_UNITS` (and `systemd-timesyncd`, which owns UDP 123) are stopped, never disabled, and listed in
`evidence/stopped-units.txt`. `core.env` is rendered once and then left alone, so values you add by hand survive.

`/run` is wiped at every reboot, so the Core runtime directory (`RUNTIME_DIR`, default `/run/aegis-live`) is gone after one; `aegis-live-up.sh` re-creates it (`install -d -o <core user> -m 750`) before it starts the Core, and a Core started by hand needs the same directory first.

## Flashing the controller

1. Build from the same commit as the Core: `cd firmware && pio run -e esp32dev`. The broker CA is compiled in from the
   gitignored `firmware/src/secrets.h` (copy `secrets.h.example`); the NTP address is the AP address.
2. Record `firmware.bin` and its sha256. Provision the NVS image (namespace `aegis-p1`: device id, Wi-Fi, broker host,
   MQTT user and secret, NTP, the two keys, sequence) with `deploy/pr11-phase4/p4-nvs-provision.py`. Keep the image
   out of Git (it holds the secrets).
3. **Switch the relay module's supply off while flashing** (remove the relay VCC/JD-VCC feed). In the lab the first flash
   failed with "Failed to leave compressed flash mode" and succeeded after the relay 5 V was removed and the USB cable was
   changed; the two changes were made together, so which one mattered was not isolated. Keep both as the procedure.
4. Back up first. A full 4 MB read failed on the lab board ("Corrupt data"), so the lab kept a partial image of
   `0x0–0x10000` plus the previous application image, which is enough to return to the earlier firmware.
5. Flash at 115200 baud with `esptool write_flash --verify`: bootloader `0x1000`, partition table `0x8000`, `boot_app0`
   `0xe000`, application `0x10000`, NVS `0x9000` (size `0x5000`). A verify mismatch at `0x9000` after the first boot is
   normal: the radio stack adds its own NVS namespaces; check that `aegis-p1` is intact.
6. Reconnect the relay supply and let the ESP32 boot. It must come up in LOCKDOWN (fail-secure) and stay there until the
   first RESTORE.

Rollback of the controller: `write_flash --verify 0x0 <partial backup> 0x10000 <previous application image>`.

## Relay wiring: COM–NO on this module

The relay module used in the lab is active-low and is **energized in NORMAL**: with the system in NORMAL the continuity
path is COM–NO, with LOCKDOWN it opens. That is the opposite of the documented COM–NC circuit, so the lab wired the
protected conductor through COM and NO and left NC unused. No firmware change was made. Check your own module before
trusting either contact: put a meter across the protected conductor and compare NORMAL and LOCKDOWN. The module's
supply/jumper arrangement (VCC and JD-VCC) was not recorded in the lab notes; record it when you wire yours.

Physical proof is a meter reading, never the ACK: closed in NORMAL, open in LOCKDOWN. A cable tester through a
home-made breakout can mislead (in the lab it did not show pin 2, and a short to a neighbouring pin is suspected, not
confirmed); use the meter across the conductor as the primary reading.

## CUT and RESTORE from the control Desktop

```bash
deploy/live-lab/run-control-desktop.sh
```

It starts `tools/live_purple_control_desktop.py` with the CUT and RESTORE channels, the Core's `status.json` and the
Core user. CUT and RESTORE use different secrets that you type in the window; the Core verifies them and nothing stores
them. RESTORE needs a reason (12–240 characters) and the typed phrase `RESTORE UPLINK`. Command-line alternative:
`deploy/live-lab/owner-restore.sh "reason"`.

Expected: CUT -> device ACK -> `STATUS LOCKDOWN` with the command nonce -> meter open. RESTORE -> ACK -> `STATUS NORMAL`
-> meter closed. A CUT sent while the device is already in LOCKDOWN is reported but changes nothing.

## Telegram

Add `AEGIS_TG_TOKEN` and `AEGIS_TG_CHAT` to `etc/core.env` yourself (never commit them), then restart the Core
(`sudo systemctl restart aegis-live-core`). The Core sends one message on each LOCKDOWN/NORMAL transition and one status
report after a restart. Delivery runs in a background thread with a 10 s limit and one retry; failures print
`Telegram notification delivery failed (attempt n/2, <type>)` to the unit's journal, without the token or chat id.
Telegram is notification only and can never carry CUT or RESTORE authority.

## Pending RESTORE after a controller reboot

If the ESP32 loses power after a RESTORE was published but before the matching status arrived, the Core keeps an in-memory
"awaiting physical confirmation" state and refuses the next RESTORE with `RESTORE_ALREADY_PENDING`. Restart the Core to clear
it. Main never restores on its own: a restart issues no RESTORE, the device stays in LOCKDOWN, and the operator restores
again. The same applies after any Core restart: the device is announced as LOCKDOWN first.

## Known limits

- The lab clock: with no reachable upstream the Core's trusted time needs a kernel-synchronised clock; chrony serves a local
  stratum 10 fallback, which is a lab convenience, not a trusted time source.
- `mosquitto_passwd -b` takes the password as an argument, so it is briefly visible in the host's process list while
  `aegis-live-up.sh` runs. Single-user lab hosts only.
- Reading the unit journal needs membership of `systemd-journal` (or root); without it the Telegram failure lines are not
  visible to the operator.
- The base `live_purple_cut_desktop.py` reads a hard-coded production status path (panel shows UNKNOWN in the lab); the
  control Desktop fixes this with `AEGIS_DESKTOP_STATUS_PATH`.
- Four governance tests (release-builder / drop-in) fail on this checkout of `main` and are unrelated to CUT, RESTORE or the
  protocol; no native firmware parity environment is defined.
- After a confirmed RESTORE, a lockdown the Core did not command (dead-man's switch, power loss, a frozen Core) is refused by the next RESTORE with
  `RESTORE_ALREADY_PENDING` until a CUT replaces the Core's record or the Core restarts (workaround: CUT, then RESTORE). Finding F-A1-1 and the
  drafted fix are in `19_FAILURE_MODE_TESTS.md`.
- Scenario 3 of `16_GRADUATED_RESPONSE.md` (detector to automatic CUT) and the detector path in general are NOT part of this
  runbook's acceptance; they need the extra root helpers listed in that document.
