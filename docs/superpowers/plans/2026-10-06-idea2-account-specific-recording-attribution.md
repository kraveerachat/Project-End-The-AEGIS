# IDEA2 Account-Specific Recording Attribution Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Attribute every new verified recording to the authorized viewer's logical camera alias while retaining its exact physical Node/camera and producer-generation provenance, including concurrent aliases on one physical capture.

**Architecture:** Monitor obtains alias and generation from its existing transactional server-owned demand, then sends both over the authenticated Engine stream request. StreamHub binds each viewer lease to its alias; a small shared recording-authority snapshot lets one raw camera frame queue feed independent alias-scoped writers without a second camera open. After verified NAS transfer, Monitor validates the clip against historical demand/epoch/account/Node/physical relationships, including legitimately released rows, before insertion.

**Tech Stack:** Monitor Node.js/Express/PostgreSQL, Engine Python 3.12/Starlette/OpenCV, existing Ed25519 Identity Agent ingest and NAS sync.

**Spec:** `docs/superpowers/specs/2026-10-06-idea2-account-specific-recording-attribution-design.md` (commit `60d03383b0b48e99807ee223021d8c03e28d7b30`). Owner clarifications in the 2026-10-06 written-spec approval are binding.

## Global Constraints

- One physical capture and producer generation may serve CAM-01 and CAM-02 simultaneously; alias recording lifecycles are independent.
- Server authorization and demand acquisition precede Engine fetch; browser never supplies generation, alias authority, physical identity, Engine key or storage path.
- Preserve 300-second independent alias rollover, measured logout partial, H.264/yuv420p conversion, verified transfer before publication, Archive RBAC and exactly-once demand release.
- Exact PostgreSQL BIGINT generation stays a canonical decimal string across JavaScript/JSON; Python may hold an exact integer internally and serializes it as a decimal string.
- Existing `clips.producer_generation` and demand/epoch tables are sufficient for relational provenance; do not add a migration unless a concrete blocker is demonstrated and reviewed.
- A released demand/epoch is a valid historical provenance source for a clip finalized before release and published after verification. Never require its lease to be currently active at clip ingest.
- A later `camera_assignment` revocation does not retroactively invalidate an interval captured under an authorized historical demand. Revocation blocks new acquisition, renewal and post-revocation capture authority. Publication does not require the assignment to remain current.
- Timestamp tolerance is a configurable sanity allowance, default 30 seconds, never the authorization boundary; relational demand/epoch/Node/physical provenance is primary.
- `HISTORICAL_DEMAND_ASSOCIATION=PROVEN`; `PHYSICAL_PROVENANCE=PROVEN`; `PER_FRAME_HISTORICAL_AUTHORIZATION=NOT_CLAIMED`.

## Review Focus

1. **Late CAM-02 join:** a queued frame captured before CAM-02 authorization must not enter its segment (Task 2 test).
2. **Early CAM-01 leave:** finalizing CAM-01 must not finalize CAM-02, clear physical demand or reuse CAM-01's label (Task 2 test).
3. **Delayed NAS publish:** released demand/epoch remains valid historical evidence for an interval that ended before release; a post-release new interval fails (Task 4 tests).
4. **Generation turnover:** stale same-generation replay after final physical release and lower-generation requests after supersession must not reopen writers (Tasks 1–2 tests).
5. **Clip ingest ambiguity:** wrong account, alias, Node, physical camera, duplicate storage object or impossible timestamps must create zero rows (Task 4 tests).

### Task 4: Historical, fail-closed PostgreSQL clip ingest

**Files:** Create Monitor `server/db/clipAttribution.js`; modify `server/db/store.js`; add `tests/clipAttributionPostgres.test.mjs`; modify `tests/agentIngestProvenance.test.mjs`, `tests/archiveRecordingContract.test.mjs`. No schema or migration change.

**Interfaces:** `validateClipAttribution(client, input, verifiedNode) -> { cameraId, physicalCameraId, producerGeneration, startedAt, endedAt, durationSec, filePath }` is internal only. `insertClip` calls it inside `withTransaction` and inserts the returned bound values in the same transaction. Parse `producerGeneration` with existing canonical `parseUint(..., {positive:true,max:9223372036854775807n})`, retain its string representation, and require authenticated `ed25519` Node. No `AEGIS_CAMERA_ID`, filename or legacy shared-key value is accepted as strict alias authority. The exact DB query joins historical `camera_producer_epochs` + `camera_producer_demands` + `users` + `detection_nodes` + `physical_cameras`, matching alias, non-null viewer user, generation, verified Node and registered physical camera. The lifecycle's locked authorization at demand insertion is the available historical assignment/account evidence; the schema does not independently retain assignment history. Do not predicate historical demand/epoch on `released_at IS NULL` or live lease expiry, and do not recheck current `camera_assignment` as a prerequisite for publication. A later revocation cannot retroactively invalidate already-authorized captured footage.

**Temporal policy:** Parse `AEGIS_CLIP_TIMESTAMP_TOLERANCE_S` as a bounded nonnegative configuration value, default `30`, and convert to milliseconds without loss for sanity checks. The tolerance does not grant authority; a matching historical demand, epoch, authenticated Node, registered physical camera and alias remain mandatory. Require `startedAt <= endedAt <= serverNow + tolerance`, positive finite `durationSec` within the configured 300-second segment contract plus tolerance, and a bounded difference between reported duration and `(endedAt-startedAt)`. Check `startedAt >= epoch.acquired_at - tolerance` and, when released, `endedAt <= epoch.released_at + tolerance`; for matching historical demand(s), ensure the claimed capture interval is consistent with at least one demand interval, allowing clock/close tolerance. A clip may be published long after release or later assignment revocation, but a post-revocation new demand, renewal or capture interval is not valid. Add tests at the exact default 30-second boundary, just outside it, and a configured nondefault boundary. Historical demand association is relational, not per-frame temporal proof; never claim these clocks independently prove every frame's authorization.
